# forqsite.help

Administrator documentation for [forqsite](https://github.com/nullvalues/forqsite) —
the self-hosted, multi-tenant website builder.

**Live site:** the address is per-deployment and is published outside this tree, in the
repository's homepage/website metadata.

## Why this repo exists

Every other forqsite property (including forqsite.com) is dogfooded as a tenant on a
forqsite installation. **This site deliberately is not.** It is plain, self-contained
HTML with zero runtime dependencies: no server, no database, no build step. The docs
stay available even when a forqsite instance is down.

## Contents

| File | What it is |
|---|---|
| `index.html` | The docs site. Builders (dev setup, daily runbook), self-hosters (non-docker production install, systemd supervision, operations, backup & recovery, provider lifecycle), and reference (searchable env-var table, architecture/topology, dev→prod pipeline map). |
| `gap-handoff.html` | Known gaps between the dev environment and an operable production deployment (10 items, GAP-003 to GAP-014; a closed gap's number is never reused): what a self-hoster will hit, where to look, how to fix it, and how to tell when it is fixed. Linked from the docs sidebar. |

Each file is a single fully-inlined HTML document (fonts, styles, and scripts embedded).
They work offline, from `file://`, or behind any static file server.

## Hosting

Anything that serves static files works as-is:

```
# Caddy — replace example.com with this deployment's own address, and
# /srv/site with wherever this repo's files are checked out on that host
example.com {
    root * /srv/site
    file_server
}
```

GitHub Pages, nginx, or `python3 -m http.server` are equally fine. No headers,
rewrites, or MIME tricks required.

## Updating

These files were originally generated by a Claude design session against the forqsite
repo. They are not synced with forqsite live. They are reconciled at each docs release
instead: every claim is checked against the new forqsite commit by walking its history back
to the release commit the pages are pinned to, and claims whose evidence moved are updated
before the release. `docs/claims-manifest.json` lists those claims.
`scripts/stale-claims.py` walks that history and lists every claim whose evidence no
longer holds at the new commit, and every closed gap that has reopened. It reads a
local forqsite clone named by `FORQSITE_CLONE`, which must already contain the target
commit, and it never edits the manifest, the pages or the clone. Rewriting a stale
claim is still a reviewed story.

```sh
FORQSITE_CLONE=<path to your forqsite clone> python3 scripts/stale-claims.py <commit-ish>
```

It exits 0 when nothing is stale, and 3 when a claim is stale or a closed gap has
reopened. Its header lists every exit code.
With `--no-commits`, it prints the same verdicts without the commit lines, the target or
a renamed path's new name, so the report holds only text from the manifest and can be
quoted in a tracked file. Never commit the full report: forqsite commit subjects can
name a deployment.

### Editing the bundles

`index.html` and `gap-handoff.html` are **self-extracting bundles**, not hand-written
pages. The markup a reader sees is not in the file as markup: it lives as a
JSON-encoded template inside a `<script type="__bundler/template">` element, next to
compressed resource blobs. A text editor or a search-and-replace over the bundle
cannot safely change the page.

Use `scripts/bundle-template.py`:

```sh
python3 scripts/bundle-template.py verify  index.html              # before you start
python3 scripts/bundle-template.py extract index.html /tmp/t.html  # edit /tmp/t.html
python3 scripts/bundle-template.py inject  index.html /tmp/t.html
python3 scripts/bundle-template.py verify  index.html              # after
```

`verify` re-encodes the template already in the file and asserts the result is
byte-identical. Run it first: if it fails, the script's encoder has drifted from the
bundler's, and injecting would rewrite every byte of the template and bury the real
edit in the diff.

Two details make hand-editing unsafe and are why the script exists. The template is
JSON-encoded, so editing the escaped form by eye invites a broken string that fails
at load with no useful error. And the encoder escapes every `/` as `\u002F` — not
cosmetically: the template contains its own `</script>` sequences, which unescaped
would terminate the element carrying them and truncate the page.

Refresh passes (like Phase 2 of this project), including the rewrite of any claim the
checker reports stale, happen through the normal pairmode build loop: the refresh is
written as stories in a phase doc, then built and reviewed per-story, not applied as
freestanding hand-edits outside that process.

Content is grounded in `nullvalues/forqsite@main`. When the repo changes in ways that
affect operators (config keys, scripts, install procedure, provider loading), the docs
should be re-synced — the gap-handoff items in particular are point-in-time findings
and should be pruned as Claude Code lands them.
